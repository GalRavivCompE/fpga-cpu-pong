# Decision log

Status meanings: **open** = being explored; **provisional** = useful working choice, subject to evidence; **accepted** = selected and recorded with rationale; **excluded from v1** = deliberately outside the first ISA version; **working** = verified in implementation. A later ISA revision can change an exclusion, but an excluded feature does not silently enter v1.

| Decision | Status | Candidates / evidence needed |
| --- | --- | --- |
| CPU word width | Provisional (2026-09-22) | 32-bit general registers, using two's-complement signed interpretation and modular addition/subtraction. Compare the eventual RTL resource cost with the simpler 16-bit alternative before finalizing. |
| Instruction encoding fields | Open | Fixed 32-bit instruction width is chosen provisionally; opcode, register, and immediate field layouts remain to be designed. |
| General registers | Provisional (2026-09-22) | Eight 32-bit general-purpose registers named A–H. Three bits identify a register in an instruction. This uses a smaller register file and fewer encoding bits than RISC-V's 16- or 32-register base variants, but may require extra RAM accesses in programs with many live values. Fixed 32-bit instructions do not become shorter merely because register fields are smaller. |
| Register names versus memory addresses | Provisional (2026-09-22) | A–H name the eight CPU registers; they are not data-memory addresses. Data and program addresses are numeric byte locations in separate logical spaces. A register may contain a numeric data address: if B holds 256, `LOAD A, [B]` reads data memory at address 256 into A. A destination may also be a source, as in `ADD A, A, C`; sources are read before the result is written. Direct numeric memory operands are a separate possible assembler convenience, not part of the current instruction encoding. |
| Register operand order | Provisional (2026-09-22) | Binary register arithmetic (`ADD`, `SUB`, `MUL`, `DIV`, `MOD`) and bitwise logic (`AND`, `OR`, `XOR`) use `INSTRUCTION dst, src1, src2`, reading both old source values before writing `dst`. Unary `NOT` and one-bit shifts use `INSTRUCTION dst, src1`; `ADD_CONST` uses `dst, src1, signed_imm16`. |
| Conditional operand count | Open (2026-09-22) | The current draft uses `IF_* src1, src2, N`, where N counts following instructions and is not a register. A suggested simpler form is `IF_* src1, src2` with an implicit one-instruction skip on false; larger blocks would use `GHOST` and sometimes the opposite condition. Decide after reviewing a concrete block example. |
| GHOST count source | Open (2026-09-22) | Current `GHOST N` embeds a fixed numeric skip count, usually calculated from an assembler label. Consider a register-count form for a skip distance that changes while a program runs. This may add an opcode or operand-mode rule; `JUMP_REG` already supports jumps to computed absolute program addresses. Decide from a program that needs a runtime-variable skip. |
| Flags and detailed memory map | Open | Decide whether any condition flags are needed after drafting complete example programs; assign data RAM and peripheral addresses before RTL. |
| Microarchitecture | Open | A simple multicycle CPU is a plausible starting point; compare against single-cycle complexity after ISA sketch. Avoid a pipeline initially unless there is a measured need. |
| HDL and simulator | Open | Choose based on learning preference, board tools, and ability to run automated simulation locally. |
| FPGA board | Open | Check cost/availability, tool support, on-chip memory, I/O voltage/connectors, and a usable input/output path. |
| First physical output | Open | LEDs, serial terminal, or display. Video connector and monitor support matter if selecting video. |
| Game input | Open | Buttons or other controller; synchronize physical inputs in hardware. |
| First game | Provisional | Pong-like rules, because a small state update can be tested independently of rendering. |
| Software/hardware boundary | Provisional | CPU computes game state and rules; hardware handles physical I/O and optional video timing/rendering. |
| First hardware priority | Accepted (2026-09-22) | Get a functioning CPU running on an FPGA board first. Initial output may be LEDs or serial; video follows when useful. This is a project priority. |
| Project documentation | Accepted (2026-09-22) | Maintain this public repository as the project record, with reproducible milestone notes and explicit planned/working status. |
| Primary project objective | Accepted (2026-09-22) | Learning and understanding take priority over finishing a polished demo. Use design exercises, predictions, review, and small tests; document the reasoning behind implementation choices. |
| ISA comparison method | Accepted (2026-09-22) | Compare major design choices with established ISAs such as RISC-V, explaining similarities and differences before deciding what to adopt. |
| ISA design discussion method | Accepted (2026-09-22) | For each design problem, consider viable options and tradeoffs. Treat existing ISAs as references; document why a feature is adopted, adapted, or intentionally different so the custom ISA has a coherent design. |
| Addressing and first load/store size | Provisional (2026-09-22) | Memory addresses identify bytes. The first CPU supports aligned 32-bit loads and stores; byte and halfword operations can be considered later. This keeps the initial datapath and memory interface simple while allowing finer-grained accesses in a future extension. Similar to RISC-V's byte-addressed space and word operations. |
| Smaller memory transfers | Excluded from v1 (2026-09-22) | Version 1 has only aligned 32-bit `LOAD` and `STORE`; byte and halfword instructions are not part of its opcode set. The first board demo and word-sized game state do not require them. A future version can add them with an explicit ISA revision and a byte-order rule. |
| Load/store address forms | Accepted for v1 (2026-09-22) | Each load/store uses exactly the numeric address held in a register; v1 has no offset field or base-plus-offset opcode. Software calculates a different address with arithmetic first. This replaces the earlier proposal to encode both forms separately. |
| Bitwise NOT | Provisional (2026-09-22) | A direct instruction flips all 32 bits of a source register and writes the result to a destination register. Logical NOT (zero/nonzero to Boolean) is a separate possible operation. RISC-V expresses bitwise NOT as an assembler alias for XORI with -1. |
| Bitwise logic gates | Provisional (2026-09-22) | Keep `AND`, `OR`, and `XOR` as direct instructions. Each applies the corresponding familiar logic-gate operation independently at all 32 bit positions. `NOT` likewise inverts all 32 bits; it is not a one-bit Boolean test. |
| Shift operations | Revised provisional (2026-09-22) | Use one-bit `SHL1 dst, src1` (left, zero fill), `SHR1 dst, src1` (right, copy old top bit), and `SHR_ZERO1 dst, src1` (right, zero fill). Larger shifts repeat the operation in software. The zero-filling right shift avoids an extra mask when manipulating unsigned values. Names are provisional. |
| Alternate left fill and rotate | Excluded from v1 (2026-09-22) | No edge-copying left shift or rotate opcode in v1. The ordinary left shift fills with zero; no current example program needs another leftward bit operation. |
| Register copy | Provisional (2026-09-22) | Keep `MOVE dst, src1` as a direct instruction that copies the 32-bit value of one register into another. A load reads from data memory instead; copying through memory would require extra operations. The dedicated instruction makes simple register-to-register transfer clear in assembly. |
| Arithmetic with an embedded constant | Provisional (2026-09-22) | Include `ADD_CONST dst, src1, signed_imm16`. It adds a signed 16-bit constant to a full 32-bit register value, keeping the low 32 bits. A negative constant can decrement a counter, so a separate `SUB_CONST` is unnecessary. The operation is optional for computational completeness but saves setup instructions and scarce registers in loops; the list-sum example drops from 15 to 13 instructions and frees two registers. The name replaces the confusing `ADD_SMALL` working name. |
| Multiply and divide | Provisional (2026-09-22) | Include register-to-register `MUL` and `DIV` in the target ISA. `MUL` writes the low 32 bits of the product. `DIV` uses signed two's-complement operands and truncates the quotient toward zero. Division by zero causes a hardware fault without writing the destination. The exceptional quotient `-2147483648 / -1` wraps to `0x80000000`. Implementation timing remains open; these instructions need not run in the earliest board self-check. |
| Remainder | Provisional (2026-09-22) | Include `MOD dst, src1, src2` in the target ISA. It uses signed operands and returns the remainder consistent with `DIV` truncating toward zero: `src1 = quotient × src2 + remainder`, so `-17 MOD 5 = -2`. A zero divisor causes the same hardware fault as `DIV` without writing the destination; `-2147483648 MOD -1 = 0`. `MOD` may share division hardware, but that implementation choice remains open. |
| Conditional and skip operations | Provisional (2026-09-22) | `IF_EQ src1, src2, N` compares two registers; if equal, the following N machine instructions execute normally, and if not equal they are skipped. `GHOST N` unconditionally skips the following N machine instructions. The operations are separate; an `IF_EQ` block can control a `GHOST`. Compared with RISC-V's BEQ, which branches to a PC-relative target when equal, this design uses counted sequential skipping and needs instruction-count semantics. |
| Comparison conditions | Provisional (2026-09-22) | Keep `IF_EQ`, `IF_NE`, `IF_GT`, and `IF_UGT` as direct counted conditions. `IF_GT` compares two's-complement signed values; `IF_UGT` compares the same 32-bit patterns as unsigned values. Equality and inequality are independent of signedness. A false condition skips the next N machine instructions. |
| Backward loop operation | Provisional (2026-09-22) | `REPEAT N` jumps back N machine instructions from its own position. `GHOST N` provides forward movement. The assembler should accept a backward label and calculate N, so source code need not count instructions manually. Exact field size and range remain open. |
| No-op instruction | Provisional (2026-09-22) | `GHOST 0` advances to the next instruction without changing registers or data memory. A separate `NOP` opcode is unnecessary and is removed from the current ISA draft. |
| Stop and error behavior | Provisional (2026-09-22) | `HALT` stops successfully; `ERR_HALT` lets a program deliberately stop with a failure status. Invalid instructions, bad alignment, unmapped data access, and invalid program targets stop automatically with a hardware fault status identifying the cause. The board diagnostic interface remains to be designed. |
| Continuing warning instruction | Excluded from v1 (2026-09-22) | No `ERR_WARNING` opcode. The program can intentionally stop with `ERR_HALT`; a warning that continues would require extra reporting and clearing rules without a current use case. |
| Register-target jump and call | Provisional (2026-09-22) | Include `JUMP_REG target_reg` and `CALL_REG target_reg, link_reg` in the ISA draft for reusable functions. `JUMP_REG` loads the PC from the target register. `CALL_REG` reads the old target value, saves the following instruction address (`PC + 4`) in a chosen writable link register, then jumps to the target. Returning uses `JUMP_REG link_reg`; nested calls must preserve the link value in data memory. A target must be a valid aligned program address. Exact encoding and assembler calling convention remain open. Compared with RISC-V JALR and Astro8 JREG, this gives the counted-skip ISA a general indirect transfer without a dedicated hardware return stack. |
| Loading constants | Provisional (2026-09-22) | `SET_CONST dst, imm16` sign-extends the 16-bit constant to 32 bits, so `0xFFFF` becomes `0xFFFFFFFF` (signed -1). `SET_HIGH dst, imm16` replaces bits 31:16 while preserving bits 15:0; the pair can construct any 32-bit pattern. A fixed 32-bit instruction cannot also contain a full 32-bit immediate plus opcode/register fields. This avoids a mandatory constant table in data memory; initialized data remains available for arrays and other program data. `SET_CONST` replaces the confusing `SET_SMALL` working name. Exact binary encoding remains open. |
| Instruction width | Provisional (2026-09-22) | Fixed 32-bit instructions. This makes counted skipping straightforward: advance the byte-addressed PC by four bytes for each skipped instruction. RV32I also uses fixed 32-bit base instructions, though it has an optional compressed extension; the reason here is to simplify the first implementation of counted skips. |
| Instruction/data memory organization | Provisional (2026-09-22) | Keep separate logical instruction-fetch and data-load/store address spaces in the first CPU (Harvard-style programmer-visible organization). `LOAD`/`STORE` and memory-mapped I/O use the data space; program fetch uses the instruction space. This makes the fetch-versus-data distinction explicit and supports a simple read-only program memory plus writable data memory. It means constants needed by a running program must be encoded in instructions or initialized in data memory; programs cannot read their own instruction words as data. This ISA-level choice is distinct from using separate physical FPGA RAM blocks: RISC-V specifies one byte-addressed address space even though a RISC-V implementation may use separate physical instruction/data paths or memories. |

## Evidence and change rule

Record each accepted decision with date, rationale, alternatives, and the measurement or simulation that supported it. If a later test contradicts the rationale, revise the choice and note why. Mark features **working** only after a reproducible simulation or hardware observation, with the command or procedure recorded here.
